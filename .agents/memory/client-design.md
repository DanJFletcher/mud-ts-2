---
name: Client design priorities
description: User direction for MUDD's gameplay UI, navigation, and mobile priority.
---

- Mobile is the most important layout.
- The game should have a tight, focused UI around what the player is doing and the actions they can take, not feel like a marketing website.
- Traveler info and Field notes should be separate screens the player navigates to.
- Marketing language can be reserved for the main home or login page, not gameplay.
- Play uses one terminal: show only the current room name above the transcript, emit default `look` output on room entry, include NPCs present in the room description, scroll the transcript independently, dock the command field, show no message counts, allow the terminal to collapse to its room header, and support full-screen mode.
- Replace Available paths with a shared room-chat window for players in the same room; keep its embedded Play panel fixed-height, collapsible to the header, and independently scrolling, while full-screen mode fills the viewport. Place a collapsible map beneath chat; it tracks the current and previously visited locations. NPC room announcements belong in chat, private NPC dialogue stays in the terminal, and dialogue progress is scripted, character-specific, and only available while co-located.
- Quest progress belongs to the individual character and is derived from server-recorded actions. Accept and report quests through private NPC dialogue; show active and completed objectives in Field notes. The first quest slice has a narrative-only completion. Play's terminal announces newly completed active objectives once and does not replay old objective notices on load.
- On Play, a horizontal right swipe opens room chat full-screen and a left swipe opens the visited-location map full-screen. A downward swipe on the terminal header opens the terminal full-screen; an upward swipe on its header, close control, or Escape returns to gameplay. In full-screen chat, a left swipe, close control, or Escape returns to gameplay; in the map, a right swipe, close control, or Escape closes the map. Preserve vertical scrolling and do not trigger from form controls.
- Quick commands should stay compact: neither page has a visible category label; the main page offers Look, Read, Drop, and Go, while the second offers Take and Help. Quick Look and Take list only items still in the current room. After a quick action submits, return to the main page.
- Initial `read` support targets signs and markers in the character’s current room; inventory items are not readable yet.
- Targeted `look [at] <object>` describes a visible object’s appearance; `read <object>` returns its written text. Both are limited to the current room.

**Why:** The user asked for NPCs in the room to appear in room descriptions.

**How to apply:** Include each current-room NPC's name and description in the text returned by `location.describe`; keep targeted NPC look and dialogue as separate actions.

**Why:** The user approved objective-completion feedback in the terminal so progress is clear during play rather than only in Field notes.

**How to apply:** Announce only when successful reads or movement update server-projected active objectives. Seed known completions from the initial snapshot so reloads do not replay old notices.

**Why:** The user rejected marketing-like gameplay copy and asked for a terminal-focused Play view. Room descriptions should come from default `look` output rather than duplicate static text; quick controls should center on actions, not event counts. The user asked for compact quick-action pages with no visible category labels, Take and Help on a second page, no quick targeting of items already picked up, room descriptions that omit items after pickup, and quick actions that return to the main page after submission. The user wants the terminal collapsible while retaining its room header and openable full-screen by a downward header swipe. Room chat is public to players sharing a room; the embedded chat should stay fixed-height and collapsible while full-screen chat fills the viewport. The user asked for a map below chat that keeps character-specific position history and can also collapse. NPC public announcements use chat, while private NPC conversations remain in the terminal. The user approved scripted NPC dialogue with character-specific persistent progress and requested swipe navigation between chat and map. The user asked to build an event-backed, per-character quest flow; keep the first quest's completion narrative-only rather than introducing an economy.

**How to apply:** Prioritize mobile gameplay; keep the room name as context, put room descriptions and command results in the terminal transcript, keep its history and room-chat history independently scrollable, dock commands at the bottom, omit activity counts, replace Available paths with a compact room-chat window, and keep movement available through Go quick actions. The terminal can collapse to its room header, hiding its transcript and command controls until expanded. A downward swipe from the terminal header opens it full-screen, and an upward header swipe, close button, or Escape closes it; keep normal transcript scrolling uninterrupted. The embedded room-chat panel has a fixed height, can collapse to its header, and scrolls messages within the panel; the map sits below chat, collapses to its header, and marks the current location separately from rooms visited by this character. Full-screen chat and map use the available viewport height. A right swipe in Play opens chat and a left swipe opens the map; a left swipe closes full-screen chat and a right swipe closes the full-screen map. Close buttons and Escape remain available, while vertical scrolling and form controls are unaffected. Room chat is shared only by occupants of the current room and supports NPC-originated broadcasts; keep private NPC dialogue in the terminal, restrict it to NPCs in the player's current room, and save dialogue progress to the individual character rather than the account. Keep Take and Help on the second quick-action page, return to the first page after executing a quick action but not after opening a selector, limit quick Look and Take targets to objects still present in the current room, include takeable-item room descriptions only while those items are in that room, and resolve typed `look [at] <target>` and `read <target>` against their supported objects. Quest accept/turn-in actions must be validated on the server against the character's current room and recorded event stream. Keep quest state per character; project objective completion from recorded reads and movement, and place the journal on Field notes rather than crowding Play.
