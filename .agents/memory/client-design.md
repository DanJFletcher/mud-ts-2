---
name: Client design priorities
description: User direction for MUDD's gameplay UI, navigation, and mobile priority.
---

- Mobile is the most important layout.
- The game should have a tight, focused UI around what the player is doing and the actions they can take, not feel like a marketing website.
- Traveler info and Field notes should be separate screens the player navigates to.
- Marketing language can be reserved for the main home or login page, not gameplay.
- Play uses one terminal: show only the current room name above the transcript, emit default `look` output on room entry, scroll the transcript independently, dock the command field, and show no message counts.
- Replace Available paths with a shared room-chat window for players in the same room; keep its embedded Play panel fixed-height, collapsible to the header, and independently scrolling, while full-screen mode fills the viewport. NPC room announcements belong in chat, private NPC dialogue stays in the terminal, and dialogue progress is scripted, character-specific, and only available while co-located.
- On Play, a horizontal right swipe opens room chat full-screen; a left swipe, close control, or Escape returns to gameplay. Preserve vertical scrolling and do not trigger from form controls.
- Quick commands should stay compact: neither page has a visible category label; the main page offers Look, Read, Drop, and Go, while the second offers Take and Help. Quick Look and Take list only items still in the current room. After a quick action submits, return to the main page.
- Initial `read` support targets signs and markers in the character’s current room; inventory items are not readable yet.
- Targeted `look [at] <object>` describes a visible object’s appearance; `read <object>` returns its written text. Both are limited to the current room.

**Why:** The user rejected marketing-like gameplay copy and asked for a terminal-focused Play view. Room descriptions should come from default `look` output rather than duplicate static text; quick controls should center on actions, not event counts. The user asked for compact quick-action pages with no visible category labels, Take and Help on a second page, no quick targeting of items already picked up, room descriptions that omit items after pickup, and quick actions that return to the main page after submission. Room chat is public to players sharing a room; the embedded chat should stay fixed-height and collapsible while full-screen chat fills the viewport. NPC public announcements use chat, while private NPC conversations remain in the terminal. The user approved scripted NPC dialogue with character-specific persistent progress. The user also asked for a right-swipe full-screen chat gesture with accessible close alternatives.

**How to apply:** Prioritize mobile gameplay; keep the room name as context, put room descriptions and command results in the terminal transcript, keep its history and room-chat history independently scrollable, dock commands at the bottom, omit activity counts, replace Available paths with a compact room-chat window, and keep movement available through Go quick actions. The embedded room-chat panel has a fixed height, can collapse to its header, and scrolls messages within the panel; full-screen chat uses the available viewport height. A right swipe in Play opens room chat full-screen; a left swipe, close button, or Escape closes it, while vertical scrolling and interactive controls remain unaffected. Room chat is shared only by occupants of the current room and supports NPC-originated broadcasts; keep private NPC dialogue in the terminal, restrict it to NPCs in the player's current room, and save dialogue progress to the individual character rather than the account. Keep Take and Help on the second quick-action page, return to the first page after executing a quick action but not after opening a selector, limit quick Look and Take targets to objects still present in the current room, include takeable-item room descriptions only while those items are in that room, and resolve typed `look [at] <target>` and `read <target>` against their supported objects.
