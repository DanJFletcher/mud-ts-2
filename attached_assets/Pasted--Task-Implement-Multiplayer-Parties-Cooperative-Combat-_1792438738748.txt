# Task: Implement Multiplayer Parties, Cooperative Combat, and Party Quests

## Objective

Implement a multiplayer party system that allows players to create, join, manage, and leave parties of up to four players.

Party members must be able to participate in cooperative combat on the same team and undertake special party quests.

This feature must follow the project's existing **modular, plugin-first architecture**, maintaining a clear separation between reusable engine capabilities and game-specific rules.

The engine should provide generic player grouping, membership management, and cooperative combat infrastructure without hard-coding party sizes, quest requirements, or other gameplay-specific decisions.

**Party chat is explicitly out of scope and will be implemented separately.**

## 1. Party Creation and Management

### Creating a Party

A player can create and host a party using:

`party create`

The player automatically becomes the party host and first member.

Example terminal output:

```text
====================================
          PARTY CREATED
====================================

Party ID: ABC123
Host: PlayerA
Members: 1 / 4

Other players can join using:
party join ABC123
====================================
```

Requirements:

- Each party has a unique identifier.
- Each party has exactly one host.
- A party supports a maximum of four members, including the host.
- Players can only belong to one party at a time.
- Party creation and membership changes are validated server-side.
- Players cannot create another party while already belonging to one.

### Joining a Party

Players can discover available parties using:

`party list`

Players can join using:

`party join <party-id>`

For the initial implementation, parties are publicly joinable without requiring invitations or host approval.

Example:

`You joined PlayerA's party! (2/4 members)`

All existing members are notified when another player joins.

If a party is full, joining must fail with an appropriate message.

The design should allow future plugins to introduce private parties, invitations, approval workflows, or matchmaking without requiring an engine redesign.

### Viewing Party Information

Players can enter:

`party info`

The terminal displays the party host, party identifier, current members, and maximum capacity.

### Leaving a Party

Any non-host member can enter:

`party leave`

The player is removed from the party and all remaining members are notified.

The departing player immediately loses access to the party's active quests and future cooperative encounters.

Their departure must not automatically delete the remaining party's quest progress.

### Closing a Party

The host can enter:

`party close`

Closing the party must:

1. Remove all players from the party.
2. Notify every connected member that the party has closed.
3. End or invalidate all active party quests.
4. Delete all temporary party quest progress.
5. Release party-related resources and remove the party from active listings.

For the initial implementation, if the host explicitly leaves the party, treat that as closing the party. The host should receive clear confirmation of this consequence.

Host transfer can be implemented later.

## 2. Cooperative Combat

Party members must be able to fight together as allies in the same combat encounter.

### Expected Behavior

When a party member initiates or joins an eligible combat encounter:

- Other eligible party members participate in that encounter.
- All participating party members are assigned to the same combat team.
- Enemies are assigned to the opposing team.
- The existing combat system handles initiative, turns, attacks, targeting, damage, and encounter resolution.
- Each player independently controls their own character.

Example:

```text
====================================
         COMBAT BEGINS
====================================

Your party encounters 3 Goblins!

ALLIES
- PlayerA (Host)
- PlayerB
- PlayerC

ENEMIES
- Goblin 1
- Goblin 2
- Goblin 3

Rolling initiative...
====================================
```

### Combat Architecture

Extend the existing combat system to support multiple player-controlled combatants belonging to the same team.

Avoid implementing a separate party combat engine.

The combat system should support reusable concepts such as:

- Combat encounter participants
- Team or faction assignments
- Ally and enemy identification
- Multiple player-controlled characters
- Turn ownership and action authorization
- Encounter lifecycle events

**Party membership and combat team membership must remain separate concepts.** A party is a persistent social grouping during its lifetime; a combat team belongs to a specific encounter.

A combat encounter may have participants who are not part of a party.

Reuse existing combat mechanics wherever possible, including the dice/RNG and turn-management plugins.

### Combat Eligibility

Respect existing game-world rules for proximity, location, character availability, and combat participation where those systems already exist.

Do not automatically pull unavailable, disconnected, or geographically ineligible members into combat.

The exact rules governing who may participate should be configurable at the game-plugin level, not hard-coded into the engine.

### Compatibility with PvP Consent

The existing consent-based PvP system must remain functional.

Being in a party must not bypass PvP consent requirements or allow players to attack other players without authorization.

Keep PvP consent rules independent of party membership.

## 3. Party Quest System

Introduce support for quests that can only be started by players who belong to an active party.

Party quests should reuse the existing quest system wherever possible rather than creating an entirely separate quest engine.

### Quest Eligibility

A quest can be designated as a party quest through its game-defined configuration or metadata.

For example, a quest might expose an eligibility condition indicating that active party membership is required.

The engine must not hard-code specific party quest types or objectives.

Requirements:

- Ordinary quests continue to work as before.
- Party quests cannot be started by players who are not in a party.
- A player hosting a party is considered a party member.
- The game plugin validates party eligibility before starting a quest.
- A party quest belongs to a specific active party instance.

### Shared Quest Progress

Party quests must support shared progress.

For example:

```text
====================================
          PARTY QUEST
====================================

Quest: Goblin Extermination

Objective:
Defeat 10 Goblins as a party.

Progress: 6 / 10

Party Members:
- PlayerA
- PlayerB
- PlayerC
====================================
```

When an eligible party member defeats a goblin, the quest progresses for the party.

Requirements:

- All members of the same party see the same quest progress.
- Relevant events are counted only for the party that owns the quest.
- Multiple party members can contribute.
- Contributions must not be double-counted.
- Other parties cannot modify or inherit that progress.
- Quest objectives and completion rules remain defined by the game plugin.

For the MVP, support one active instance of a given party quest per party unless the existing quest system already supports a more flexible model.

### Temporary Quest Progress

**Party quest progress must exist only for the lifetime of the party.**

When a party closes or disbands:

- All incomplete party quests are abandoned.
- Their progress is permanently discarded.
- Players cannot recover or resume that progress by creating a new party.
- A newly created party starts its quests from zero.

Use a party-specific identifier to associate quest instances with the party.

The implementation may use an in-memory or persistent data store, depending on existing architecture, but progress must be removed or invalidated when its owning party ends.

If a player leaves an active party:

- They lose access to that party's quests.
- They cannot continue contributing to those quests.
- The remaining party retains its progress.
- A future party does not inherit their previous progress.

Completed quest rewards, if applicable, should follow existing game reward mechanisms. Do not revoke legitimately earned rewards when the party disbands.

Avoid introducing new reward mechanics as part of this task.

## 4. Engine Architecture

### Engine Responsibilities

The engine should expose generic functionality for:

- Creating and destroying player groups.
- Managing group ownership and membership.
- Enforcing membership and authorization constraints.
- Publishing group lifecycle events.
- Identifying group members for other plugins.
- Supporting team-based combat encounters.
- Allowing plugins to subscribe to relevant membership, combat, and quest events.

Prefer extending the existing plugin infrastructure.

Possible generic lifecycle events include:

```text
group.created
group.member.joined
group.member.left
group.closed
```

Event names are illustrative. Follow the repository's existing naming conventions.

The engine should not need to understand the gameplay meaning of a party.

### Game Plugin Responsibilities

The game plugin should define:

- The maximum party size of four players.
- Party-related terminal commands.
- Rules for creating and joining parties.
- Player-facing party notifications.
- Cooperative combat participation rules.
- Party quest eligibility and progress policies.
- Behavior when the host closes or leaves.
- Gameplay restrictions involving party membership.

Where practical, these behaviors should be configurable so other games built on the engine can define different party systems.

### Client Responsibilities

The initial implementation should target the existing terminal client.

The terminal must provide commands for creating, listing, joining, inspecting, leaving, and closing parties, and display notifications about membership changes.

The server must remain authoritative over all party state and gameplay decisions.

Future GUI, mobile PWA, and voice clients must be able to implement their own party interfaces using the same underlying APIs and events.

## 5. Party Lifecycle and Edge Cases

Ensure the following situations are handled correctly:

- A player cannot belong to two parties simultaneously.
- A party cannot exceed four members.
- Simultaneous join requests cannot exceed the capacity limit.
- Closing a party invalidates its identifier and prevents further joins.
- A player cannot close a party unless they are its host.
- Repeated leave or close commands are handled safely.
- Players cannot access another party's private state or quests.
- Temporary network disconnections should not immediately destroy party membership where reconnect support exists.
- Explicitly leaving or closing a party must be distinguished from a temporary disconnection.
- Active combat encounters must remain consistent if party membership changes during combat.
- Changes to party membership must not silently reassign combat participants in an ongoing encounter.
- Party quest progress must not leak between parties or survive disbanding.
- State-changing operations must be validated and handled atomically on the server.

Follow existing session management conventions for reconnection and cleanup.

## 6. Terminal Commands

Implement or extend the terminal command registry with:

| Command | Description |
|---|---|
| `party create` | Create and host a party |
| `party list` | List available parties |
| `party join <id>` | Join a party |
| `party info` | Show current party information |
| `party leave` | Leave the current party |
| `party close` | Close the party (host only) |
| `party help` | Display available party commands |

Party-related commands should follow existing terminal parsing, validation, and help conventions.

## 7. Testing and Acceptance Criteria

Implement automated unit and integration tests covering:

### Party Management

- [ ] Players can create parties.
- [ ] Players can join existing parties.
- [ ] A party supports a maximum of four members.
- [ ] Concurrent joins cannot exceed capacity.
- [ ] A player cannot join multiple parties.
- [ ] Members can voluntarily leave.
- [ ] Hosts can close parties.
- [ ] Party members receive lifecycle notifications.
- [ ] Invalid and unauthorized operations are rejected.

### Cooperative Combat

- [ ] Party members can participate in the same combat encounter.
- [ ] Party members are assigned to the same team.
- [ ] Each player controls only their own character.
- [ ] Existing initiative and turn mechanics work with multiple players.
- [ ] Combat eligibility follows existing game rules.
- [ ] Leaving a party does not corrupt an active combat encounter.
- [ ] PvE and consent-based PvP remain functional.

### Party Quests

- [ ] Party quests cannot be started outside a party.
- [ ] Party members can contribute to shared objectives.
- [ ] All party members can view shared quest progress.
- [ ] Progress is isolated between different parties.
- [ ] Progress remains available to remaining members when one leaves.
- [ ] Departed members lose access to the party's quests.
- [ ] Disbanding a party invalidates and deletes its incomplete quest progress.
- [ ] Creating another party does not restore previous progress.
- [ ] Ordinary quests remain unaffected.

## 8. Out of Scope

Do not implement the following in this task:

- Party chat
- Party matchmaking
- Private party invitations or passwords
- Host transfer
- Party loot distribution rules
- Party-wide XP sharing rules
- Raid groups larger than four players
- New quest reward systems
- A separate party-specific combat engine

These features may be developed later as additional plugins or extensions.

## 9. Implementation Process

Before modifying code:

1. Inspect the existing repository architecture and relevant documentation.
2. Identify the existing systems for players, sessions, plugins, commands, combat, quests, and event delivery.
3. Determine which reusable capabilities already exist.
4. Implement the smallest architectural changes necessary.
5. Build the party gameplay functionality on top of those capabilities.
6. Add automated tests and update relevant developer documentation.
7. Verify the feature using multiple independently connected clients.

Do not perform unrelated architectural refactoring.

## 10. Final Deliverables

Implement the feature directly in the existing project.

Provide a final summary explaining:

1. The architectural changes made to the engine.
2. The game-level party plugin implementation.
3. How cooperative combat is integrated with existing combat mechanics.
4. How party quests and their temporary progress work.
5. How group lifecycle events are exposed to other plugins.
6. How to manually test the feature using four connected players.
7. Any limitations or deferred functionality.

**Primary architectural principle:** The engine should know how to manage groups and combat teams, but should not know what a party means, why it has four members, or what makes a quest a party quest. Those decisions belong to the game plugins.
