# MUDD Repository Audit — Agent Handoff

**Repository:** https://github.com/DanJFletcher/mud-ts-2  
**Audited revision:** `48bd96333372f0d2e9a898b4e00483b894ad5378` (`main`, 2026-10-18)  
**Method:** Read-only static GitHub source inspection. No runtime, PostgreSQL migration, lint, test, typecheck, or production build was executed. Confirm reproductions with automated tests before altering behavior.

## Executive assessment

Keep the current modular TypeScript monorepo. It has substantial functioning implementation: Zod wire contracts, an engine host and plugin registry, an event-store port with PostgreSQL and in-memory adapters, optimistic stream versioning and command receipts, a separate HTTP client SDK, Drizzle schemas/migrations, original demo-world content, account/character roster, NPC dialogue, quests, room chat, and a mobile-first React PWA plus accessible UI primitives and tests.

**Primary architectural risk:** a character-stream model works for the solo demo but does not yet govern shared state in a multiplayer MUD. Resist expanding combat, economy, land ownership, and MUD-Lang before deciding ownership and authority for shared world entities, items, occupancy, and side effects.

Priority levels: **P1** = repair before enabling real multiplayer or deploying to untrusted public traffic; **P2** = fix in the next architecture/quality pass; **P3** = documented extension, not an MVP defect.

## P1 — Confirmed functional defects

### 1. Chat acknowledgements can skip messages unseen by the polling cursor

**Evidence:** [RoomChatPanel.tsx lines 113–150, 163–193](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/apps/web/src/RoomChatPanel.tsx#L113-L193)

`lastMessageIdRef` is correctly advanced by polling, but a successful `POST /api/chat` also sets it to the max ID returned by the send acknowledgement. If other users' messages were inserted between the last poll and the acknowledgement, the next `afterId` starts after them; these messages can be permanently absent from the displayed chat.

**Change:** Maintain a server-feed cursor advanced exclusively from sequentially retrieved history, not optimistic/sent acknowledgements. Merge acknowledgement messages into the display by ID without moving the fetch cursor. If using a cursor-based subscription later, define backfill and gap recovery.

**Acceptance test:** At cursor 10, another user posts 11, current user sends 12, next poll must retrieve and render 11 exactly once. Include NPC response 13, rapid room switching, and reconnect tests.

### 2. Duplicate successful move requests can re-trigger non-idempotent NPC announcements

**Evidence:** [server/index.ts lines 356–402](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/apps/server/src/index.ts#L356-L402), [engine.ts lines 177–220](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/packages/engine-core/src/engine.ts#L177-L220), [npc-announcer.ts](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/apps/server/src/npc-announcer.ts).

The engine returns a successful receipt for a duplicate command ID; the HTTP route treats *all* successful `character.move` receipts as newly committed arrivals and calls `announceNpcsOnEntry`. The in-process cooldown may mask the issue but cannot establish durable exactly-once semantics across retries, restarts, or server replicas.

**Change:** Propagate `committed | duplicate | conflict` from append through `DispatchResult`; only fire arrival effects on newly committed transitions. Prefer a transactional outbox with unique event/consumer key for durable domain side effects; a simple committed-only guard is an acceptable immediate fix.

**Acceptance test:** Replaying the exact move command ID produces the same receipt, only one movement event, and no second announcement even after cooldown expiration and server restart.

### 3. Plugin dependency version checks accept incompatible versions

**Evidence:** [engine.ts lines 50–56](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/packages/engine-core/src/engine.ts#L50-L56).

`dependencyVersionMatches` matches only the major version whenever the range matches a `^?X.Y.Z` pattern. For example, a requirement of `^1.5.0` incorrectly accepts `1.0.0`; an exact requirement `1.5.0` incorrectly accepts `1.0.0`.

**Change:** Use a tested SemVer range evaluator (for example `semver.satisfies`) or an explicitly documented, correctly implemented supported subset. Reject unsupported version-range syntax rather than silently passing.

**Acceptance test:** Exact, caret, compatible minor/patch, lower-than-required, major mismatch, invalid range, dependency cycle, and missing dependency.

## P1 — Data consistency, trust and production-readiness gaps

### 4. Room items are character-owned, not world-instance-owned

**Evidence:** [character.ts lines 69–104 and 207–268](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/packages/plugins/src/character.ts#L69-L104), [replay.ts](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/packages/engine-core/src/replay.ts).

Take/drop events are recorded only in the acting character's stream. `location.describe` calculates room takeables from *that character's* `itemLocations` and immutable room definitions. Therefore two different characters in the same world instance can take their own copy of the same defined item. `occupants` is also hardcoded to `[]` in `character.ts` line 261. This is acceptable if the current demo intentionally has per-character instancing, but must not masquerade as shared MUD simulation.

**Change:** Write an ADR defining world instance, room, entity instance, character inventory, and possession ownership boundaries. When enabling shared objects, give each runtime item a stable instance ID and a single authoritative holder/location, and transact pickup/drop against a world-owned aggregate or cross-stream consistency mechanism. Keep personal inventories as character projections of ownership facts; distinguish instanced/personal loot intentionally.

**Acceptance test:** Two players in the same world instance contend for one unique item; exactly one takes it. A drop becomes visible to the other player. Instance boundaries prevent bleed-through; room occupants are filtered to permitted viewers.

### 5. Room chat bypasses the engine's command/event path

**Evidence:** [index.ts lines 289–354](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/apps/server/src/index.ts#L289-L354), [room-chat-service.ts](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/apps/server/src/room-chat-service.ts).

Room messages and NPC reactions are directly inserted into a separate table, bypassing the plugin command registry, authoritative event store, and receipt idempotency semantics. This may be a sensible specialized chat persistence choice, but it lacks a documented separate aggregate/protocol boundary and transactional guarantees with movement. An in-flight chat request can validate a room, then the character can move before message insertion.

**Change:** Decide explicitly whether chat is a separate durable service/domain log or an engine plugin. In either case, specify server-authorized room membership at the commit boundary, idempotent message submission, monotonic room cursors, ordering, anti-spam limits, and reconnect semantics. Do not automatically force all ephemeral chat into character event streams.

**Acceptance test:** Concurrent move/chat cannot produce a message in a room the player is no longer authorized to speak in under the chosen ordering policy; repeated submit ID does not duplicate a message; messages are isolated by world instance.

### 6. Error handling conflates game-rule failures and infrastructure failures

**Evidence:** [engine.ts lines 160–226](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/packages/engine-core/src/engine.ts#L160-L226).

`EngineHost.dispatch` catches any thrown error from store read, handler, or append and returns `RULE_VIOLATION` with raw `error.message`. A PostgreSQL failure therefore appears as a player rules error and potentially exposes backend/SQL details. `EngineHost.query` similarly returns thrown error messages to clients as `INTERNAL_ERROR`.

**Change:** Introduce typed domain errors and known client-safe messages, with unknown errors mapped to `INTERNAL_ERROR` and a correlation ID, and detailed stack/context logged only on the server. Preserve distinct conflict vs validation vs transient failure policies.

**Acceptance test:** A DB outage returns generic 5xx/internal error information, not an SQL string or rules error; an invalid exit gives a safe `RULE_VIOLATION`; stale versions return `VERSION_CONFLICT`.

### 7. Deployment security and abuse controls need hardening

**Evidence:** [index.ts lines 119–127, 319–354](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/apps/server/src/index.ts#L119-L127), [Clerk proxy middleware](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/apps/server/src/middlewares/clerkProxyMiddleware.ts).

Credentialed CORS is configured with `origin: true`, reflecting arbitrary origins, and no explicit chat or command rate limiter is visible. This does not by itself demonstrate an exploitable cross-origin credential leak; it is an unnecessary public API exposure that requires a deliberate threat-model review. The proxy also relies on forwarded host/protocol information: verify the actual deployment edge overwrites those headers and configure trusted proxies/hosts.

**Change:** Restrict allowed origins, define CSRF controls appropriate to Clerk's cookie/token model, establish trusted-proxy/host rules, and enforce per-actor/IP limits for chat, auth-adjacent and expensive commands. Add request-size and abuse tests.

**Acceptance test:** Unapproved origins cannot access credentialed API responses; unauthorized and forged requests fail; chat spam is throttled with a documented safe error.

## P2 — Architecture and quality

### 8. No verified PostgreSQL end-to-end suite or checked-in CI workflow

**Evidence:** [server integration test](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/apps/server/src/npc-room-announcement.integration.test.ts) uses module mocks, including database and engine. Repository tree contains no `.github/workflows` file and no dedicated `postgres-event-store.test.ts`. The commit's combined GitHub status returned no statuses. This is not proof that tests fail; it means the current audit cannot establish production DB behavior.

**Change:** Add test PostgreSQL (container or ephemeral test DB) to CI and verify migration application, concurrent revision conflicts, idempotency under parallel requests, account/character isolation, item projections, and server restart/replay. Run `npm ci`, `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`, and Storybook build in CI. Preserve existing unit/component tests.

### 9. Event replay is not fail-closed on unrecognized events and inconsistent on validation

**Evidence:** [replay.ts lines 13–223](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/packages/engine-core/src/replay.ts#L13-L223).

Known event types are handled with an `if/else` chain, but an unexpected event type is silently ignored. Some handlers parse complete event contracts, while rename/archive/restore access raw payloads or coerce with `String(...)`. Under future schema evolution, unsupported events can produce subtly stale projections instead of an explicit compatibility error.

**Change:** Implement a versioned event decoder/upcaster and exhaustive reducer routing. Reject unknown character-stream event types or document explicit forward-compatible skipping where safe. Validate all payloads consistently. Add replay migration tests.

### 10. Plugin manifest and capabilities are partly aspirational

**Evidence:** [engine.ts](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/packages/engine-core/src/engine.ts), [plugins.ts contracts](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/engine-contracts/src/plugins.ts).

Dependency order/cycles and missing capabilities are enforced, but manifest permissions are not runtime access controls; capabilities are untyped string identifiers with a generic cast; the proposal in `engine-contracts` differs from the live host's plugin types. The core currently trusts every loaded plugin's code. This is acceptable for built-ins but not a safe arbitrary mod execution platform.

**Change:** Reconcile live plugin and contracts interfaces, define typed/versioned capability tokens, explicit permission grants and a trust boundary. Document first-party trusted plugins vs third-party scripts and when isolation becomes necessary. Avoid building a sandbox prematurely; do not advertise untrusted plugins as safe.

### 11. Snapshot consistency and performance must be designed before concurrent players scale

**Evidence:** [index.ts lines 258–287](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/apps/server/src/index.ts#L258-L287), [character.ts state.load](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/packages/plugins/src/character.ts), [postgres-event-store.ts readStream](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/apps/server/src/persistence/postgres-event-store.ts).

`/api/game` reads character events for `character`, then the engine independently rereads the stream for `location`. Concurrent writes can create mixed revisions in one response. Each command/query replays the entire history from the beginning, so long-lived character streams become increasingly expensive.

**Change:** Read a consistent character projection once per request (or assert a shared revision/cursor) and pass it to projection builders. Add snapshot/checkpoint support when measurements justify it; do not prematurely build event infrastructure more complex than the workload.

### 12. API contract, docs, accessibility and dependency hygiene

- [SDK lines 321–334](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/packages/client-sdk/src/index.ts#L321-L334): HTTP responses are trusted by TypeScript casts rather than parsed against Zod schemas. Introduce response schemas and structured command-error types, especially before third-party clients or TTY.
- [ARCHITECTURE-M1.md](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/docs/ARCHITECTURE-M1.md): still documents guest HTTP-only sessions, while [session-service.ts](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/apps/server/src/session-service.ts) requires Clerk authentication. Record this as a superseding ADR and amend scope/current architecture docs.
- [WorldMapPanel.tsx](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/apps/web/src/WorldMapPanel.tsx) and [RoomChatPanel.tsx](https://github.com/DanJFletcher/mud-ts-2/blob/48bd96333372f0d2e9a898b4e00483b894ad5378/apps/web/src/RoomChatPanel.tsx): fullscreen surfaces declare modal semantics and initially focus close controls but do not visibly enforce modal focus containment. Test focus trap, Escape, focus return, reduced motion and touch alternatives.
- Root tracks both `package-lock.json` and `pnpm-lock.yaml`, while scripts use npm. Pick the canonical package manager and enforce a single authoritative lockfile.

## P3 — Deliberate next capabilities, not present defects

1. Client protocol/version compatibility and a small independently packaged TTY client using the same SDK semantics.
2. Shared room occupancy, subscriptions, globally ordered delivery cursors, reconnect/backfill, and simultaneous-player simulations.
3. Ruleset-neutral dice/RNG and clock ports integrated into the live host before a combat/turn plugin; do not implement D&D combat logic directly in networking, client, or core dispatch.
4. Explicit authoring/content-pack import pipeline with content versions, validation, provenance, and migration handling.
5. Future crafting, resource gathering, property, economy and MUD-Lang as opt-in plugins using reviewed capabilities. Do not bury these systems in `apps/server/src/index.ts`.
6. For any D&D-derived publicly distributed game data, verify licensing and use appropriately licensed SRD material or original content rather than assuming the Player's Handbook, Monster Manual or published adventures are redistributable.

## Implementation sequence for the coding agent

**PR 1: Correctness and test coverage** — Fix chat-cursor skip, semver checks, duplicate-move NPC announcements, and safe error classification. Write regression tests FIRST; preserve current demo behaviors.

**PR 2: Production safety** — Implement CORS/trusted-host constraints, anti-abuse policy, and real Postgres concurrency/idempotency tests. Add CI across tests, lint, typecheck and builds. Ensure deployed configuration is documented.

**PR 3: World-state ADR + narrow implementation** — Decide whether current takeables are player-instanced or genuinely shared. Document world-instance/character/room/item aggregate boundaries, implement the smallest appropriate shared-state slice, and test two separate logged-in players.

**PR 4: Contract cleanup** — Event decoder/upcaster, projection-revision consistency, typed SDK response validation, plugin API reconciliation, updated architecture docs, single package-manager lockfile, and modal accessibility tests.

**Scope discipline:** Do not rewrite the monorepo, swap its stack, or add combat/economy/crafting/land ownership/MUD-Lang in this hardening pass. Work in small reviewed commits, preserve one active character per account/world session, and preserve the mobile-first PWA and Storybook boundary.

## Agent completion report format

For every PR: state root cause, changed files, new regression tests and their exact commands/results, migration or rollback effects, remaining risk, and whether the behavior was verified against real PostgreSQL. When a recommended fix conflicts with current user-facing design, record the tradeoff in an ADR before changing functionality.
